<objective>
Make the web server adapter (`MyWSGIRefServer`) safe to stop at any point of its startup and unable to hold the process open, then run the phase gate.

Purpose: plan 129-01 bounded the wait on the web-server thread. Three gaps remain that would defeat it. First, stopping the server is itself not bounded: `stop()` today calls the web server library's `server_close()`, which tears down the worker pool on the job thread and takes about half a second for each browser request that is stuck (measured: 2 s with four, 5 s with ten), all before the 5 s wait even starts, so the two together can pass Docker's 10 s limit and the final state save is lost (129-REVIEWS.md, HIGH concern). Second, if shutdown arrives in the short moment before the server thread has created its server, `stop()` fails today and the server then starts anyway and serves forever, keeping the web port (a restart would then fail to bind). Third, the web server library starts 10 worker threads that Python waits for at exit, so the process still hangs whenever the server was not stopped cleanly, even though the server thread itself is now a background thread. This plan closes all three: `stop()` only closes the listening socket and returns at once, leaving the worker teardown to the server thread (which the 5 s wait and the background-thread setting already cover); it proves the first gap closed with real stuck requests and the third with a real child process.

Output: changes to `MyWSGIRefServer` in `src/python/web/web_app_job.py`, new tests in `src/python/tests/unittests/test_web/test_web_app_job.py`, and the filled-in `129-VALIDATION.md`.
</objective>

src/python/web/web_app_job.py, adapter as it stands before this plan (plan 129-01 does not touch it):
```python
class MyWSGIRefServer(bottle.ServerAdapter):
    quiet = True  # disable logging to stdout

    def __init__(self, logger: logging.Logger, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.logger = logger
        self.server = None

    @overrides(bottle.ServerAdapter)
    def run(self, handler):
        self.logger.debug("Starting web server")
        handler = TransLogger(handler, logger=self.logger, setup_console_handler=(not self.quiet))
        self.server = httpserver.serve(handler, host=self.host, port=str(self.port), start_loop=False,
                                       handler=MyWSGIHandler,
                                       **self.options)
        self.server.serve_forever()

    def stop(self):
        self.logger.debug("Stopping web server")
        self.server.server_close()
```

Verified behaviour of the installed paste 3.10.1 (129-RESEARCH.md experiments E1-E7 and revision experiments R1-R6):
- paste's serve loop is `while self.running: handle_request()` with a 1 s timeout on the listening socket, and its `finally` calls `thread_pool.shutdown()` with the default force_quit_timeout=0 on the server thread. Setting `server.running = False` and calling `server.socket.close()` is therefore a complete stop: the port is free at once, the loop ends within about 1 s, and paste drains its own worker pool on the server thread. Measured: stop() returned in 0.00 s in every case; the server thread ended after about 1.0 s when idle, 1.5 s with one stuck request, 3.0 s with four and 6.0 s with ten (the last one is what the 5 s join bound and its warning are for).
- paste's `server_close()` does those same two things and then calls `thread_pool.shutdown(60)` on the calling thread. Measured from the job thread: about 0.5 s per stuck worker (0.5 s with one, 2.0 s with four, 5.0 s with ten), so it is not bounded and it runs before the 5 s join. If a worker that paste killed earlier is still alive, the same call enters paste's force-quit branch, which is written to end the process with os._exit(3); on Python 3 it raises AttributeError first (atexit._exithandlers no longer exists), so stop() fails instead. Never call server_close() or thread_pool.shutdown() from stop().
- Between `httpserver.serve(...)` returning and `serve_forever()` starting, the socket is bound and listening but nothing has been accepted and all ten workers are idle. server_close() at that point, on the server thread, drains ten idle workers in milliseconds and cannot meet a stuck worker. That is the only place it may be called.
- The stop-before-serve and the running-server stop were both re-run with this design (R1-R6): early stop ends the thread at once with the port closed; os._exit was never reached in any run.
- socketserver's shutdown() never returns with paste (deadlock). Never call it.
- paste's 10 pool workers are non-daemon unless daemon_threads=True is passed to httpserver.serve; non-daemon workers keep the process alive at exit.
- self.options is empty in this codebase, so daemon_threads=True does not collide with **self.options.
- paste accepts port "0" and binds an ephemeral port; the bound port is server.server_address[1].

Lock convention, src/python/controller/file_operation_manager.py lines 101-104: `self.__processes_lock = threading.Lock()` declared next to the state it guards, with a comment naming the two threads involved.

Patch target for the paste module: `web.web_app_job.httpserver`.
