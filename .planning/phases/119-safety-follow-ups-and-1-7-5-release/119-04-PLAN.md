<objective>
Build the completion-evidence foundation for IMP-02 as two new, independently testable modules: `ArrQueueClient` (HTTP to Sonarr/Radarr `/api/v3/queue/details` on a bounded daemon worker with a non-blocking start/poll handoff) and `CompletionGate` (snapshot cache, capped backoff, strong-identity match, verdict, lifecycle-scoped proof cache, hold registry with transition-only logging). No controller wiring in this plan — 119-06 wires it (and consumes a proof on transfer submission); 119-07 feeds `holds` into the model and invalidates proofs on lifecycle reset / root removal.

Codex adversarial findings and the plan checker shape the design. Rewrite 1: (1) a proof cached by name + remote size would stay PROVEN across a same-name re-grab whose client preallocated the original size, bypassing both submission checks — so proofs carry a download identity, live evidence is evaluated first and overrides the cache, and an explicit `invalidate` hook exists; (3) dropping malformed queue records before deciding completion converts uncertainty into PROVEN — so malformed records are preserved as `valid=False` and hold the root they match. Rewrite 2: (1b) `invalidate` that only drops `_proofs` leaves the completed record in `_snapshots` until the refresh deadline, so a verdict taken in that window recreates PROVEN from stale evidence, and a configuration key of service codes only lets an arr URL switch reuse the old server's snapshots — so invalidation fences the name per target (on snapshot generations in rewrite 2; on request-start epochs since pass 4, below) and the cache is keyed by full integration identity; (3b) a buffered `requests.get` enforces the size cap only after downloading everything — so the response is streamed with bounded accumulation. Rewrite 3: (1c) a deadline checked only between `iter_content` chunks cannot interrupt a read blocked inside urllib3 (`HTTPResponse.stream` on a non-chunked body blocks until `amt` bytes arrive or the connection closes — verified in the installed requests 2.34.2 / urllib3 2.8.0), so a trickling Content-Length body that sends a byte every few seconds defeats both the 10 s inactivity timeout and the chunk-boundary deadline and pins the controller thread — so the HTTP work moves to a daemon worker (one in flight per target); (2c) the pass-2 fence blocked PROVEN until EVERY enabled arr had a post-invalidation fetch, silently restoring the all-services-available requirement that D-17 rejects — so the fence is evaluated per target: stale targets cannot prove, fresh targets can, and a responding arr's fresh strong proof releases the item alone. Rewrite 4 (checker iteration 2): rewrite 3 still had the controller thread `join(timeout=FETCH_DEADLINE_SECS)` on the worker, so one evaluate() with two stalled arrs could block the single ControllerJob thread for ~40 s — delaying STOP/DELETE/EXTRACT commands and webhook-import processing and violating the `Controller.process()` / `Job.execute()` "return relatively quickly" contract — so the controller thread now NEVER waits: `start_fetch` spawns and returns, `poll` reads a lock-protected handoff slot and returns, the gate decides from the latest completed snapshots, and a target whose first/forced fetch is still in flight produces a provisional hold instead of a wait. Codex pass 4 (finding 2): a fence recorded on result-consumption generations is satisfied by a request that STARTED before the invalidation and COMPLETED after it — a delayed response for the earlier download lands after the same-name lifecycle reset, bumps the generation past the fence and authorizes copying its still-downloading replacement — so freshness is now keyed on request-start epochs: `start_fetch` stamps the pending fetch with the target's current invalidation epoch, a snapshot carries its request's epoch, and only a snapshot whose request started at or after the fence is fresh. RESEARCH's architecture diagram and its "oversized/malformed arr response stalls the controller" threat row describe `(3.05, 10)` timeouts as the mitigation; that mitigation is superseded by this plan (timeouts remain as a worker-side bound only).

Purpose: implement the exact queue predicate verified in RESEARCH (D-05) amended by D-16/D-17, so a sparse-file size plateau can never start a transfer and an unavailable/ambiguous/missing/unverifiable arr entry always holds — without letting the evidence fetch itself delay command processing, model updates or webhook handling by even one socket round-trip.
Output: `src/python/controller/arr_queue.py`, `src/python/controller/completion_gate.py`, and their unit test files (Wave 0 gaps from VALIDATION.md).
