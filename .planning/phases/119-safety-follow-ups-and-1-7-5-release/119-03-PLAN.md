<objective>
Add the explicit submitted-but-unobserved guard to the auto-delete Timer (DEL-01, backlog 999.3), mirroring `CommandProcessor._is_submitted_unobserved` (409 for manual Delete/Extract). Today protection is indirect (evidence gate + stale-retained model state); the Timer × unavailable-status × submitted-root combination is untested, and the set is read cross-thread without a lock.

The set guard alone is not sufficient (codex adversarial finding 2, verified against HEAD): `Controller.__process_commands` releases `__model_lock` before `CommandProcessor.handle` submits, and `__execute_auto_delete` releases `__model_lock` before `delete_local`. A Timer can pass every guard on an empty submitted set, a concurrent QUEUE can then submit the root, and the Timer can delete the copy lftp is writing. Closing this requires serializing the *decision-to-destructive-operation* window with the *submission* window: a per-root operation reservation (`RootReservations`) shared by queue submission and both deletion paths.

Holding the reservation only until `delete_local` returns is not enough either (codex pass-4 finding 1, verified against HEAD): `FileOperationManager.delete_local` L151-172 constructs a `DeleteLocalProcess`, appends a `CommandProcessWrapper` to `__active_command_processes`, calls `start()` and returns True immediately; the `os.remove` / `shutil.rmtree` runs in the child for seconds to minutes (the incident root was 77 GB). A QUEUE that acquires the reservation right after the Timer's `delete_local` returns submits a transfer whose files the still-running child then deletes. The reservation must therefore live as long as the child: ownership is transferred to the wrapper at the `delete_local` call and released by `cleanup_completed_processes` — which `Controller.process()` L278 calls every cycle — once `is_alive()` is False, regardless of exit status, with inline release on launch failure and a sweep in `stop()` so nothing can leak.

And the hand-off must not open a window of its own (codex pass-5 finding, verified: an unstarted `multiprocessing.Process` returns `is_alive() == False`). At HEAD `delete_local` appends the wrapper and THEN calls `start()` (L170-171). If the Timer thread is descheduled between the append and `start()`, `Controller.process()` on the controller thread runs `cleanup_completed_processes`, sees `is_alive() == False`, treats the never-started child as finished, runs the callback and — with the pass-4 design — releases the reservation; a QUEUE for the root is then accepted, and the Timer subsequently starts a deletion that is neither tracked nor protected. The fix chosen here is **start, then register**: `process.start()` runs first and the wrapper is appended under `__processes_lock` only after `start()` has returned, through a single private `__launch_and_track(wrapper)` helper used by every wrapper creation (`delete_local` and `delete_remote`). Rationale over an explicit STARTING/RUNNING launch state: cleanup only ever iterates registered wrappers, so if nothing unstarted can be registered there is no state for cleanup to check, no extra branch in the sweep, and the invariant is one grep (`start()` line precedes the only `append` line). On `start()` failure nothing is appended and the reservation is released inline.

Purpose: a pending auto-delete can never delete a transfer that was just submitted and not yet observed, and can never overlap a submission in flight — before, during or after the deletion subprocess, including the instant between creating and starting it; it defers and retries safely through the existing bounded re-arm machinery (ROADMAP success criterion 2).
Output: lock-protected submitted set with add-before-queue ordering, the Timer guard, the per-root reservation wired into Controller, CommandProcessor and FileOperationManager with process-lifetime ownership and start-then-register launch, and RED-first regressions including barrier-controlled concurrency tests, asynchronous-lifetime tests and the launch-window test.
</objective>

New module contract (this plan CREATES it; 119-06 Task 3 reuses it unchanged):
- `src/python/controller/root_reservation.py`: `class RootReservation` — attributes `name`, `holder`; `release() -> None` idempotent and owner-checked (removes the registry entry only if that entry IS this token; a second call or a call after a newer holder took the name is a no-op; never raises); `__enter__` returns self, `__exit__` calls `release()`. `class RootReservations`: `acquire(self, name: str, holder: str) -> Optional[RootReservation]` — non-blocking, returns None when another holder owns the name; `holder_of(self, name: str) -> Optional[str]`; internals `threading.Lock` (leaf: never held while calling out) + `Dict[str, RootReservation]`. No callbacks, no logging, no persistence. Stdlib only.
- Ownership rule (document in the module docstring): the acquirer owns the token until it either calls `release()` / exits the `with`, or passes it to `FileOperationManager.delete_local(file, reservation=token)`. From the moment `delete_local` is ENTERED the manager owns it and guarantees release on every outcome (launch failure → released before the exception propagates, wrapper never tracked; child exit with any status → released by `cleanup_completed_processes`; shutdown → released by `stop()`). Between entry and the end of `start()` the token is held by nobody-but-the-call-in-progress: it is not in the wrapper list, so cleanup cannot touch it, and it is not released. The caller must not release after a hand-off (harmless if it does — idempotent — but it would reopen the window early, so the Timer and CommandProcessor use a `handed_off` flag).
