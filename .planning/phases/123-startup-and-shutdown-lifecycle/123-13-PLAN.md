<objective>
Close GAP-2 (the D-01 lftp half). On DEV_PIN_GAP, both active-transfer restarts (123-12 A1, A2) logged `ERROR Error stopping lftp during controller exit` with `PtyProcessError: Could not terminate the child.` 1.65-1.80 s after SIGTERM. Idle restarts never did.

Diagnosis, settled from source (code references are in the installed venv, pexpect 4.9.0 / ptyprocess 0.7.0, found with `cd src/python && poetry run python -c "import ptyprocess,pexpect;print(ptyprocess.__file__,pexpect.__file__)"`):
- What the error literally means. `Lftp.exit()` (src/python/lftp/lftp.py:451-463) calls pexpect `spawn.close(force=True)` (pexpect/pty_spawn.py:317-331), which calls `PtyProcess.close(force=True)` (ptyprocess/ptyprocess.py:393-409). That closes the pty fd and waits `delayafterclose` (0.1 s). Then `terminate(force=True)` (ptyprocess.py:622-660) sends SIGHUP, SIGCONT, SIGINT and SIGKILL, waiting `delayafterterminate` (0.1 s) after each. It raises `PtyProcessError('Could not terminate the child.')` only if `isalive()` (a `waitpid(pid, WNOHANG)`) still reports the lftp pid unreaped 0.1 s after SIGKILL. pexpect re-raises it as `ExceptionPexpect` (`_wrap_ptyprocess_err`, pty_spawn.py:19-25) before setting `closed`, so nobody reaps the child afterwards.
- Rejected: "tini's group SIGTERM hit lftp". `pty.fork()` makes lftp the leader of its own session and process group (RESEARCH lines 53-56), and `tini -g` (entrypoint.sh:111) signals only python's group. lftp never sees the container SIGTERM. Even if it did, it would die sooner, not later.
- Rejected as the cause of the error: "a zombie ptyprocess doesn't reap". `isalive()` calls `waitpid`, which reaps a zombie and returns False. A zombie cannot produce this error. It is, though, the leak the error leaves behind: after the raise, the SIGKILLed lftp becomes a zombie that nothing reaps until python exits. On a container restart that is harmless. On the in-process controller restart (RECOV-01 ServiceRestart, which also calls Controller.exit()) it accumulates.
- Rejected as the cause of the error: "lftp's children keep the pty open". `isalive()` tracks only the lftp pid, and children holding the pty cannot keep that pid alive. lftp's sftp `ssh` children lose their channel when lftp dies. The live sampler (123-14) checks that they are gone.
- Remaining cause: lftp is SIGKILLed but has not finished dying 100 ms later, and this happens only during an active transfer. A SIGKILLed process becomes reapable only when its in-kernel exit completes. A process blocked in uninterruptible I/O (state D, e.g. writing transfer data at about 60 MB/s to the NAS volume) or tearing down many sockets and dirty file pages can take longer than 100 ms. This is unit-unprovable, so the fix logs the process state (`/proc/<pid>/stat` state letter) and child count at the moment of the fallback. The 123-16/123-17 live run then confirms it (D-02 split below).
- Related risk found while diagnosing, documented by lftp, not yet observed: "If you exit lftp before all jobs are finished, lftp will move itself to nohup mode in background. The same thing happens with a real modem hangup" (lftp man page, `exit`; `cmd:move-background` defaults to true). lftp.cc `move_to_background()` forks, the child `setsid()`s, and the parent `_exit(0)`s. A job surviving `kill all` at `exit` time would leave a detached lftp in a new session that no process-group kill reaches. `exit kill` ("kills all numbered jobs before exiting") closes that path.

Fix (robust whichever in-kernel reason makes lftp slow to die): keep pexpect's own force close as the first and, on a clean shutdown, only step. That keeps the idle path byte-for-byte the same in behaviour. Only when it raises:
1. Poll `isalive()` once. This reaps it if it has meanwhile died.
2. If it is still alive, log a WARNING with the diagnostic, then SIGKILL its process group with `os.killpg(pid, SIGKILL)`. This is safe because the pid is unreaped, so group <pid> can only be lftp's own group.
3. Poll-reap on an injected monotonic clock for at most 2.0 s, then log INFO.
4. If it is still alive at the deadline, raise LftpError. That is honest: Controller.exit() logs its ERROR and the harness fails.
Also send `exit kill` instead of `exit`.

Why 2.0 s: 20x pexpect's 0.1 s post-SIGKILL check. lftp's stop then ends at most about 4 s after SIGTERM (the live error came at +1.8 s), leaving more than 5 s of docker's 10 s stop timeout for the rest of Controller.exit() (live: about 0.3 s).

Success criterion 4 ("no new sleeps"), OWNER FLAG: the poll needs a wait between checks. The plan uses an injected `waiter` (default `time.sleep`, poll interval 0.05 s). It runs only after pexpect's own force close has already failed, i.e. never on a clean shutdown (the idle regression test asserts the waiter is never called). This is the same framing D-03 uses for a bounded wait. The alternative without a wait is a blocking `os.waitpid(pid, 0)`, which is unbounded if lftp stays in state D. It was rejected because it could hang the in-process controller restart. The SUMMARY must state this flag in plain words for the owner.

D-02 split for this plan:
- Unit-proven here with fakes (no real processes, no real sleeps): the idle no-op, the fallback reap with and without the group kill, the 2.0 s bound and the honest raise, ProcessLookupError tolerance, the unchanged propagation of graceful failures, `exit kill`, and the /proc diagnostic parser.
- Live-proven only (123-16/123-17): a real active-transfer restart logs no `Error stopping lftp` / `Could not terminate the child`; the lftp pid and its children are gone before the old container stops; and the actual process state letter at the fallback, which settles the D-state hypothesis.
