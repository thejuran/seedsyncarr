<objective>
Close GAP-1 (D-01, D-07). The live restart check (123-06) still logged the false `Scanner process(es) died unexpectedly` ERROR plus `Caught exception in job ControllerJob` in 3 of 5 `docker restart` cycles. The 123-04 health check gives SIGTERM-killed scanners exactly one extra 0.5 s ControllerJob cycle. That assumes the main thread's SIGTERM handler (`Seedsyncarr.signal()` -> `Controller.note_shutdown_requested()` -> `ScanManager.note_shutdown_requested()`) runs within milliseconds. Live, it ran 0.67 to 1.55 s after the scanners died.

The fix makes the shutdown-vs-crash decision independent of handler latency. All-SIGTERM deaths get a time-bounded grace on an injected monotonic clock instead of a one-cycle grace. The window is 10.0 s, docker's default stop timeout. During a real `docker stop`/`docker restart`, either the main-thread handler runs inside the window (the INFO path) or docker SIGKILLs the container when the window ends, so the false ERROR cannot fire on that path whatever the handler latency. Every other kind of death still raises at once.

Rejected alternatives (recorded for the evidence file in 123-10):
- (b) `signal.pthread_sigmask` blocking SIGTERM in worker threads: forked children inherit the forking thread's signal mask. The scanners are started from the ControllerJob thread, so a blocked SIGTERM would be inherited and would break `AppProcess.terminate()`, which relies on SIGTERM. It also cannot cover threads created by libraries (web server, multiprocessing feeders, Timer threads).
- (c) Children handling SIGTERM themselves: changes child-process semantics more widely than this gap needs.

D-02 split for this plan:
- Unit-proven here, with a fake clock and no real processes or sleeps: the grace window, the replay of the measured 0.67 s and 1.55 s handler latencies, the bounded surfacing of a genuine SIGTERM-only death, and immediate raising for every other death.
- Live-proven only (123-11/123-12): that real restarts on the new build log neither error.
