<objective>
Make live queue completion checks normalize the stored Sonarr/Radarr key on read (ARR-02) and skip safely, with a key-free log line, when the key is missing or invalid (ARR-03).

Purpose: this is the fix for the false all-clear itself. A key saved with padding earlier in the session currently fails every real queue check while Test Connection passes. After this plan the queue check trims the same way; a key that cannot be used makes the check skip and the completion stay held, which is the existing safe outcome. No import or deletion decision changes.

Output: changes to `controller/arr_queue.py` and tests in `test_arr_queue.py` and `test_completion_gate.py`. `completion_gate.py` is not touched.
</objective>

    Gate: real client, sonarr_api_key "   " -> evaluate({ROOT: SIZE})[ROOT] == HOLD("sonarr_unavailable"), no request.
    Gate transition: real client with a valid key and a settled empty-queue fetch, then the key is changed to "abc def" -> next evaluate answers HOLD("sonarr_unavailable"), the cached snapshot is gone, no second request.
  </behavior>
  <implementation>Normalize where the config is read; validate at the single choke point before any worker exists; remember the last warned key token per arr code.</implementation>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory config -> ArrQueueClient | The stored key may be padded or invalid (saved before this phase in the same session, or set by another code path) |
| ArrQueueClient -> Sonarr/Radarr HTTP | The key becomes the X-Api-Key header of an outbound request |
| ArrQueueClient -> application log (file and live log stream) | Any logged value is visible to anyone who can read logs or the UI log page |
| ArrQueueClient -> CompletionGate | The fetch outcome feeds the decision to release or hold a completion (import / deletion safety) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
