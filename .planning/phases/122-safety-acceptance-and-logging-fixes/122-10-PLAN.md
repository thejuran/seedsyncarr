<diagnosis_refinement>
Planner verification against the code (supersedes the "root state DOWNLOADED" wording in the 122-05 diagnosis for the LIVE shape; both shapes are tested):
- `Controller.process()` runs `__update_model()` (ModelPipeline.build_and_apply_model, which ends with `_commit_downloaded_membership()`) BEFORE `__check_webhook_imports()`. `_commit_downloaded_membership` commits any root whose state is DOWNLOADED or EXTRACTED in the same cycle. So on a live build a root that is DOWNLOADED in the model is already in `downloaded_file_names` when Window 2 runs and never reaches the Ignoring branch.
- The reachable live window is therefore: the lftp job for the root has ended (no LftpJobStatus, so `_set_initial_state` leaves the root DEFAULT instead of DOWNLOADING), and the local scan is still lagging (once the root leaves `__active_downloading_file_names` it drops off the fast active scanner), so at least one child still shows local < remote with no transfer state -> child DEFAULT -> `_are_all_children_downloaded` False -> root stays DEFAULT, with root local_size < remote_size. has_evidence False, transferring False -> dropped. One or two cycles later the local scan catches up, the root becomes DOWNLOADED and commits (matches the live log: drop at 16:51:38, commit at 16:51:40).
- In unit tests the model is injected directly (`_put`) and the pipeline does not run the commit pass (existing tests call `_commit_root()` explicitly), so a DOWNLOADED-but-uncommitted root with a stale root local_size (the orchestrator's described shape) also reaches the Ignoring branch there. The RED tests cover both shapes as two separate test methods.
</diagnosis_refinement>

<fix_choice>
Chosen fix (narrow variant of 122-05's option 1, justified from the code): in Window 2's `if not has_evidence:` branch, a notice whose key is still present in `self.__pending_child_notices` at that point has, this very cycle, passed `_revalidate_pending_notice` (same lifecycle generation as when it was kept, exactly one model path, the same stored path under the same root, younger than `_PENDING_NOTICE_TTL_SECS`). It could only have been kept in the first place while the root was a remote release in DOWNLOADING/QUEUED state (`__keep_pending_notice` is only reached past the `transferring` check). That is a stronger "known-tracked root" signal than `__root_lifecycle_generation` membership (which is a defaultdict and so says nothing). For such a notice, if the root still has a remote copy (`root_file is not None and root_file.remote_size is not None`), do not drop it: take the same credit-or-keep path used while transferring (`__credit_early_child` if the child is now DOWNLOADED with local_size == remote_size, otherwise leave it pending).
Why this is safe:
- Fresh notices are unaffected: a root that is not transferring and not committed still gets the Ignoring warning for any notice that was not already pending. The 2026-08-21 foreign local-only dir case (remote_size None, never pending) is unchanged.
- Credit writes imported_children only. It never commits the root, never adds it to imported_file_names and never arms auto-delete; arming still requires a commit (has_evidence/commit path or `_commit_downloaded_membership` + arm-on-commit) and the auto-delete coverage guard still decides.
- Boundedness is unchanged: `__keep_pending_notice` does nothing to an existing key except the debug log, so inserted_at (and thus the 6 h TTL) is not refreshed; `_PENDING_NOTICE_MAX` still caps the dict; expiry, ambiguity, path change, generation change (USER requeue / lifecycle reset) and root removal still discard it in `_revalidate_pending_notice` / `_discard_pending_notices`.
- A root-level notice for a directory root is never kept pending today (dropped by `root_level_dir`), so it can never enter this path. Single-file roots, whose root-level notices ARE kept pending while transferring, get the same protection with the same semantics (kept, then accepted on commit), which is no broader than what already happens while they transfer.
Rejected: 122-05 option 2 (recompute directory local_size/remote_size from children in model_builder.py) changes every size consumer (UI, ETA, has_evidence for fresh notices) — larger blast radius and would not fix the DEFAULT-state live shape. Option 3 (coverage guard trusts on-disk completeness instead of a webhook notice) weakens the import-proof requirement for deletion — rejected as it loosens the incident protection.
Residual (documented, not in scope): a FRESH notice that first arrives inside the same post-transfer window is still ignored, as before this phase. That is the pre-existing evidence-gate behavior, not the D-06(c) deferral contract; record it in the SUMMARY under "Residual risk" so the owner sees it.
</fix_choice>
