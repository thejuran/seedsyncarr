## Summary

The leak has one source. `src/docker/build/docker-image/setup_default_config.sh` runs `cat ${SETTINGS_FILE}` at line 27 and again at line 36. `entrypoint.sh:96-99` runs that script through `gosu` on every container start. Its stdout goes straight to the container log, and on the NAS that is Docker's `db` log driver. No other startup path prints a secret value. The default-config generation step (`setup_default_config.sh:21-25`) sends both stdout and stderr to `/dev/null`. `entrypoint.sh` only prints uid/gid/path `log` lines. The Python app's only config dump is `Context.print_to_log()` (`common/context.py:57-70`), which runs at DEBUG level and redacts every current secret key. It redacts them from a hand-kept set (`_REDACTED_KEYS`, `context.py:54-55`), though, not from `Config.secret_fields()`, so a secret field added later would leak whenever debug is on. Settings reload (the UI restart, which raises `ServiceRestart`) builds a fresh `Seedsyncarr()`, so it goes through the same `print_to_log` path (`seedsyncarr.py:115`, `main()` at `:604-631`). The config-set API echoes the value in the HTTP response body only (`web/handler/config.py:128`). It never logs it, and the access log (`paste` TransLogger) records the request line, which has no body.

One behaviour of the current script shapes the fix. With an existing config, `replace_setting` (`:31`) always returns non-zero: `sed` finds no placeholder, then `grep -q` fails. Under `set -e` the script exits right there. So an existing config is dumped once (line 27) and line 36 never runs, while a fresh install is dumped twice. `entrypoint.sh:99` then logs "config setup returned non-zero (existing config — continuing)" on every normal start. If the fix just moves a status line to the end of the script, that line will never print for existing installs. Guard the replace step instead (run it only when the placeholder is present).

Testing: use a sentinel-driven pytest that runs the real bash script against a temp `settings.cfg`. Fill every `Config.secret_fields()` entry with a unique sentinel and assert that none of them appears in combined stdout+stderr. Against today's script it fails (the `cat` prints all five sentinels). It runs in CI's `unittests-python` job once `src/docker/test/python/compose.yml` mounts `src/docker/build/docker-image` read-only into the test container, because today the container only sees `src/python`. Add a Python startup/reload guard test (sentinels through `Seedsyncarr()` construction with debug on) driven by `secret_fields()`, and make `print_to_log` redact by `secret_fields()`. The release and deploy reuse 119-09/10/11 step for step. Version files, CI jobs, the smoke list and the 118-05 loader check are inventoried below. The smoke adds one count-only log check with a positive control on the 1.7.5 image.

**Primary recommendation:** Remove both `cat` lines and guard `replace_setting` behind a placeholder check. Print one `Config ready …` line that says whether the config was generated or an existing file was kept. Prove the fix with a RED-first sentinel pytest that executes the real script (mounted into the CI test container). Then release 1.7.6 through a `release/1.7.6` branch and PR exactly like 1.7.5, and deploy by digest using the 119-11 runbook.

### Pattern 1: Script fix (D-01/D-02)
**What:** Remove both dumps, guard the replace step, and print one status line.
**Example (illustrative; the planner owns the final wording):**
```bash
#!/bin/bash
set -e
CONFIG_DIR="/config"
SETTINGS_FILE="${CONFIG_DIR}/settings.cfg"
SCRIPT_PATH="/app/python/seedsyncarr.py"
PLACEHOLDER='<replace me>'

if [ -f "${SETTINGS_FILE}" ]; then CONFIG_STATE="existing config kept"; else CONFIG_STATE="default config generated"; fi

# Generate default config (all app output discarded — never echo config values)
python ${SCRIPT_PATH} -c ${CONFIG_DIR} --html / --scanfs / --exit > /dev/null 2>&1 || true

# First run only: set local_path. Never echo any other setting (D-02).
if grep -qF "local_path = ${PLACEHOLDER}" "${SETTINGS_FILE}" 2>/dev/null; then
    echo "Setting local_path to /downloads"
    sed -i "s/local_path = ${PLACEHOLDER}/local_path = \/downloads\//" "${SETTINGS_FILE}"
fi

echo "Config ready at ${SETTINGS_FILE} (${CONFIG_STATE})"
```
Effects: the script exits 0 for existing configs, so the misleading entrypoint "returned non-zero" line goes away. That is a harmless change to a non-secret diagnostic. Note: CONFIG_STATE is computed before generation, so "generated" also covers the case where the app backed up an unparsable file and wrote a default; the app logs that separately. Keep `#!/bin/bash` and the file's git mode `100755` (Pitfall 4).

### Pattern 2: RED-first sentinel shell test (D-04)
**What:** Run the real script against a temp dir and assert that no secret sentinel appears in stdout or stderr.
**How:**
1. `script = Path(__file__).resolve().parents[4] / "docker/build/docker-image/setup_default_config.sh"`. If it is missing, **fail** (not skip). A skip would let CI pass silently if the mount were dropped.
2. Copy it into `tmp_path`, replacing `CONFIG_DIR="/config"` → the tmp config dir and `SCRIPT_PATH="/app/python/seedsyncarr.py"` → a stub `stub.py` (empty file). Assert each original line occurs exactly once before replacing (guards against silent no-ops if the script changes). Do not run the real app here: with a complete config and `--exit`, `seedsyncarr.py` would start the controller and web server.
3. `sentinels = {field: f"SENTINEL-{field}-{uuid.uuid4().hex}" for (_, field, _) in Config.secret_fields()}`; also `assert len(sentinels) >= 5` (guards an empty discovery).
4. Scenarios:
   (a) existing complete config with sentinels (the production NAS case; today's script leaks via line 27);
   (b) config whose `local_path` is still `<replace me>`, with sentinels (first-run-like; today leaks via 27 and 36).
   Run each with `subprocess.run(["bash", str(copy)], capture_output=True, text=True, timeout=30, env=…)` and assert `sentinel not in stdout + stderr` for every sentinel. Report only field names on failure; the values are fake, but keep the habit.
5. Positive diagnostics remain (SEC-01): in scenario (a), assert that stdout contains the status line (e.g. `"Config ready at"`). Do not assert the exit code or the sed result in (b): host runs use macOS BSD `sed -i`, which errors (Pitfall 6).
6. Assert the source script is executable: `os.access(script, os.X_OK)`. In the CI container the bind mount keeps the host mode.

RED proof: commit the test first (`test(119.1-01): …`). Run it at that commit in a scratch worktree, as 119-09 did, and record the `failed` tail in the evidence. Expected failure: every sentinel is found in stdout.

### Pattern 3: Python startup/reload guard (D-03)
**What:** Sentinels flow through the real Python startup path with debug on. None may appear in captured log output.
**How:** Write the sentinel `settings.cfg` (with `general.debug = True`) into `tmp_path`. Patch `sys.argv = ["seedsyncarr", "-c", tmp, "--html", tmp, "--scanfs", tmp]`. Construct `Seedsyncarr()` inside `contextlib.redirect_stdout(buf)`: `_create_logger` binds `StreamHandler(sys.stdout)` at creation, so the handler writes to `buf`. Then call `Seedsyncarr._reencrypt_plaintext_if_needed`, `_emit_startup_warnings` and `_emit_decrypt_warnings` with `app.context.logger`. Assert no sentinel appears in `buf.getvalue()`. Construct twice to model a reload. Cleanup: `addCleanup(Config.set_keyfile_path, None)`, and remove the handlers from the `seedsyncarr` and web-access loggers (global logger state). Signal handlers registered in `__init__` are harmless in pytest's main thread, but you can restore them with `signal.getsignal` / `signal.signal`.
**Also:** change `Context.print_to_log` to redact any option whose name is in `{f for (_, f, _) in Config.secret_fields()}`. Keep the existing generic names (`password`, `api_key`, `secret`) as belt and braces. Add a `test_context.py` case with a real `Config` holding sentinels, using `assertLogs(level="DEBUG")`. Honest note: this test passes before the change, because today's hand list covers all five fields. It is a drift guard, not the RED demonstration. The shell test is the RED.

### Anti-Patterns to Avoid
- **Redacting the dump instead of deleting it:** D-01 forbids any value or summary. Masking also fails on multi-line values and encrypted blobs.
- **`grep -v password settings.cfg`-style filters:** a hand-kept list. The test must derive from `secret_fields()`.
- **Skipping the shell test when the script isn't found:** that turns a mount regression into a silent pass.
- **Printing captured output or real values in evidence:** count-only, as in 1.7.5.

## Common Pitfalls

### Pitfall 1: Status line never printed for existing installs
**What goes wrong:** the "Config ready" line is put at the end of the script but never appears in production.
**Why:** `replace_setting` returns non-zero whenever the placeholder is absent (`sed` no-op, then `grep -q` fails), and `set -e` exits right there (`setup_default_config.sh:4,16-17,31`). That is also why line 36 runs only on fresh installs, and why `entrypoint.sh:99` logs "returned non-zero" on every normal start.
**Avoid:** guard the replace step with a placeholder check (Pattern 1), or print the status line before it. The test's scenario (a) asserts the line is present.

### Pitfall 2: Test that can't fail or can't run in CI
**What goes wrong:** the test skips because the script isn't found in the CI container (only `src/python` is mounted at `/src`), or it uses a hard-coded field list.
**Avoid:** add the read-only bind mount to `src/docker/test/python/compose.yml`; fail on a missing script; derive sentinels from `Config.secret_fields()` and assert `len >= 5`; commit RED first and record the failing run.

### Pitfall 3: Removing the `/dev/null` redirect on the generation step
**What goes wrong:** the generation run executes the full app (`--exit`) against the real config. Its stdout (debug config dump, warnings, tracebacks) would reach the container log, and it would run twice.
**Avoid:** keep `> /dev/null 2>&1` (the duplicated `> /dev/null` can be tidied). Never add `set -x` (xtrace would echo the sed expressions and any variable).

### Pitfall 4: Losing the executable bit
**What goes wrong:** `entrypoint.sh:96` runs the script only if `[ -x … ]`. If the file is recreated with mode 644 (for example by a full-file write), first-run setup is **silently skipped** and `local_path` stays `<replace me>`.
**Avoid:** edit in place; check with `git ls-files -s src/docker/build/docker-image/setup_default_config.sh` → `100755`; the test asserts `os.access(X_OK)`. The Dockerfile `COPY` (`:135`) keeps the mode; there is no `chmod` for `/scripts`.

### Pitfall 5: `print_to_log` drift
**What goes wrong:** a future `secret=True` field isn't in `_REDACTED_KEYS`, and debug mode (which e2e turns on, `configure/setup_seedsyncarr.sh`) prints it.
**Avoid:** redact by `Config.secret_fields()` names and add the sentinel test.

### Pitfall 6: Host vs CI shell differences
**What goes wrong:** the host full-suite run (macOS, bash 3.2, BSD `sed -i` needs a suffix argument) fails scenario (b) on the `sed`, or `python` isn't on PATH.
**Avoid:** only assert sentinel absence in (b). The stub generation step is wrapped in `|| true`. Make the existing-config scenario avoid sed entirely (the Pattern 1 guard does). Run the authoritative check in CI (`make run-tests-python`, Debian, GNU sed).

### Pitfall 7: Evidence hygiene
**What goes wrong:** a smoke or deploy command prints a real value (1.7.5's step-3 grep showed the scratch webhook secret once in the terminal).
**Avoid:** use `grep -c`/`grep -cFf` only; keep values in 0600 files and pass them via `--arg`/stdin; never `cat settings.cfg`; never print `str(ConfigError)`. The positive control runs only on scratch values.

### Pitfall 8: Rotating before the deploy is final
**What goes wrong:** the owner rotates credentials, then a rollback to 1.7.4 prints the **new** credentials to the new container's log.
**Avoid:** remind the owner to rotate only after the owner confirms the 1.7.6 deploy (D-10 says "after deploy"). The rollback runbook states the caveat. If a rollback ever happens after rotation, rotate again once a fixed version is back.

### Pitfall 9: Release-branch vs main pushes
**What goes wrong:** pushing `main` before the merge publishes `:dev` and docs from an untagged tree.
**Avoid:** cut `release/1.7.6` from current local `main` (planning-only delta over `origin/main`) and open a PR; merge via `gh pr merge --merge` after owner approval, as 1.7.5 did.

### Pitfall 10: Docker build cache / stale scripts
**What goes wrong:** you suspect a stale `/scripts` layer.
**Reality:** `COPY` cache keys are content checksums, so a changed script always rebuilds that layer [CITED: docs.docker.com build cache invalidation, training-knowledge level → ASSUMED]. The real guard is the smoke step, which proves the published digest has no dump (positive control vs 1.7.5).

## Code Examples

### Sentinel config + script run (shape for Pattern 2)
```python
# Source: patterns from tests/unittests/test_seedsyncarr.py:354-370 and common/config.py:638-680
import os, subprocess, uuid
from pathlib import Path
from common import Config
from seedsyncarr import Seedsyncarr

SCRIPT = Path(__file__).resolve().parents[4] / "docker/build/docker-image/setup_default_config.sh"

def _write_sentinel_config(path: Path, local_path: str) -> dict:
    config = Seedsyncarr._create_default_config()
    config.lftp.local_path = local_path
    sentinels = {}
    for attr, field, _section in Config.secret_fields():
        value = "SENTINEL-{}-{}".format(field, uuid.uuid4().hex)
        setattr(getattr(config, attr), field, value)
        sentinels[field] = value
    assert len(sentinels) >= 5
    path.write_text(config.to_str())   # encryption.enabled is False -> plaintext, like production
    return sentinels

def _run_script(tmp_path: Path) -> str:
    text = SCRIPT.read_text()
    for old, new in (('CONFIG_DIR="/config"', 'CONFIG_DIR="{}"'.format(tmp_path / "config")),
                     ('SCRIPT_PATH="/app/python/seedsyncarr.py"', 'SCRIPT_PATH="{}"'.format(tmp_path / "stub.py"))):
        assert text.count(old) == 1, old
        text = text.replace(old, new)
    (tmp_path / "stub.py").write_text("")
    copy = tmp_path / "setup_default_config.sh"
    copy.write_text(text)
    proc = subprocess.run(["bash", str(copy)], capture_output=True, text=True, timeout=30)
    return proc.stdout + proc.stderr
```
