# Phase 119.1: Startup log secrets fix and 1.7.6 release - Context

**Gathered:** 2026-10-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Stop the container from printing configuration secrets to its stdout/container log at startup, release that fix as 1.7.6 through the same gates as 1.7.5, and deploy 1.7.6 (not the held 1.7.5) to the NAS production container by digest — replacing superseded plan 119-11. Requirements: SEC-01, REL-04, and the NAS-verification portion of REL-03 carried from Phase 119.

Root cause (found in the 119-10 smoke): `src/docker/build/docker-image/setup_default_config.sh` runs `cat ${SETTINGS_FILE}` twice (lines 27 and 36) on every container start; unchanged since v1.0.0 (`98871f5`). `entrypoint.sh` runs that script on every start. Production (1.7.4, encryption off) currently has the seedbox password and both arr API keys in plaintext in `docker logs`. The app's own plain-file logs under `/volume1/docker/seedsync/log` were checked and are clean.

Out of scope: no transfer-engine, UI, or unrelated behavior changes; no dependency churn (D-07).
</domain>

<decisions>
## Implementation Decisions

### What startup prints instead
- **D-01:** Startup prints NO `settings.cfg` values at all — not redacted, not a field summary. Replace the two `cat` dumps with a single status line such as `Config ready at /config/settings.cfg` (wording may note whether a default config was generated or an existing file was kept). Non-secret startup diagnostics that do not echo config values (entrypoint `log` lines, the app's own startup log) remain.
- **D-02:** The `replace_setting` echo (`Replacing local_path from … to …`) may stay only if it never prints a secret-marked value; it is currently only called for `local_path`. Planner may simplify it, but must not widen what it prints.

### How wide the guarantee reaches
- **D-03:** Audit ALL output from container start until the app is up: `entrypoint.sh`, `setup_default_config.sh`, any other `/scripts` run at start, and the Python app's startup logging (including config load / reload paths, e.g. config-set and settings reload, per SEC-01 "at startup or on settings reload"). Fix any other place that would print a secret-marked value.
- **D-04:** Add a regression test that fails before the fix and passes after: with a `settings.cfg` containing known sentinel values for every `secret=True` property (discovered from `Config` PROP declarations, not a hand-kept list — currently `webhook_secret`, `api_token`, `remote_password`, `sonarr_api_key`, `radarr_api_key`), the captured startup output must contain none of those values. Sentinel-based (assert on the exact values), so it also catches a leak in a new format.
- **D-05:** The 1.7.6 release smoke repeats the check on the real published image on the NAS scratch setup: a fresh container start's `docker logs` contains none of the configured secret values (count-only checks; values never printed, matching the 1.7.5 smoke hygiene).
- App runtime logs beyond startup/reload are NOT re-audited in this phase (already observed clean; a full runtime audit is out of proportion for a patch).

### Telling other users
- **D-06:** The 1.7.6 CHANGELOG and release notes carry a clear security notice: versions 1.0.0 through 1.7.5 printed `settings.cfg` — including the seedbox password, Sonarr/Radarr API keys, webhook secret and API token (plaintext when config encryption is off) — to the container log on every start. Advise users to rotate those credentials and to recreate the container (old container logs persist until the container is removed), and to check any place container logs were shipped. Plain English, no exploit detail. No GitHub Security Advisory/CVE is filed (owner choice); SECURITY.md is left unchanged unless planning finds it contradicts the notice.

### Release contents
- **D-07:** No Dependabot roll-ins in 1.7.6. Open alerts = 0 (checked 2026-10-15); open PRs #128 (Angular 22.2.2 group + dev tooling), #125 (testfixtures, dev) and #117 (puppeteer, dev) are non-security and are deferred to the Reliability milestone. Re-check open alerts at release time; a NEW runtime security alert appearing before tagging gets raised to the owner, not silently added.
- **D-08 (carried from roadmap/119):** Release through the 1.7.5 gates: release branch + PR CI green (incl. Docker build, e2e, CodeQL, packaging check), annotated tag, tag CI publishes Docker/GitHub/PyPI, smoke on the exact digest on the NAS scratch setup. Version metadata bumped to 1.7.6 everywhere 1.7.5 set it.
- **D-09 (carried, supersedes 119-11):** Deploy 1.7.6 to NAS production by digest with verified backups + loader check, digest pin (`:1.7.6@sha256:…`, never `:dev`), successful scan after any startup scanner error, arr reachability with no steady-state holds, wud restored last, rollback runbook to 1.7.4. Owner go-ahead checkpoint before the production deploy.
- **D-10 (carried):** After deploy, remind the owner to rotate the seedbox password and both arr API keys (and webhook secret / api_token if set). The old production container's logs are discarded when it is recreated.
- **D-11 (owner, 2026-10-15, added during planning):** The 1.7.6 GitHub release notes include the 1.7.5 changes in full, because most users (including production) upgrade straight from 1.7.4. Order: security notice (D-06) first, then the 1.7.6 startup-log fix, then a section like "Also in this release if you're upgrading from 1.7.4 (from 1.7.5)" carrying the full 1.7.5 "What changed for you" list, then the standard CHANGELOG link line the release-metadata check requires. CHANGELOG.md keeps normal per-version entries.
