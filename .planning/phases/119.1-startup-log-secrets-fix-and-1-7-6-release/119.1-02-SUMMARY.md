## Recorded decisions and findings

- **Catch-and-sanitize, not `interpolation=None`.** `from_str` keeps `configparser.ConfigParser()` (BasicInterpolation). Switching to `RawConfigParser` or `interpolation=None` would change how existing `%%` escapes are read. `test_from_str_double_percent_still_reads_as_percent` guards this (`a%%b` reads as `a%b`). The write side (`to_str` -> `ConfigParser.set` with a bare `%`) is still open and is Plan 119.1-06's job.
- **Value-free error.** The message is `Bad config: Lftp.remote_password could not be read (InterpolationMissingOptionError)`: section.option plus the class name, never `str(e)`. `raise ... from None` leaves `__cause__` as None with the context suppressed. The tests check `traceback.format_exception` output.
- **Fatal exit / container behaviour (from reading the files).** `entrypoint.sh:110` runs `exec gosu ... tini -g -- "$@"`, so the app's `sys.exit(2)` becomes the container's exit code. Production compose uses `restart: unless-stopped`, so a bad `%` in a secret causes a restart loop with one value-free `Fatal: ... settings.cfg was left unchanged; fix the file and restart` line in `docker logs` and the log file. That is the accepted failure mode; an unauthenticated server is not.
- **The `--exit` default-generation call cannot overwrite an existing file.** `setup_default_config.sh` runs `python seedsyncarr.py -c /config ... --exit > /dev/null 2>&1 ... || true`. That builds `Seedsyncarr()`, which raises `ConfigUnreadableError` from `Config.from_file` before any `to_file`, so the existing settings.cfg is not rewritten. The output is discarded, `|| true` lets the script carry on, and the entrypoint already tolerates a non-zero setup (`|| log "config setup returned non-zero ..."`). The real start then exits 2. Plan 119.1-01's shell test uses a stub, not the real app, so it is unaffected.
- **Grep of broad `except Exception` sites near config loading.** `Config.from_file` / `from_str` is called in exactly one product place, `Seedsyncarr.__init__` (seedsyncarr.py:66). Its `except (ConfigError, PersistError)` does not catch the new class. `run()`'s `except Exception` (line 238) wraps only the run loop after construction, so no config load happens there. `_load_persist` / `_load_controller_persist` catch `PersistError` for the persist files only. No web or controller handler loads settings.cfg from disk. Nothing turns the new error back into a reset.
- **T-119.1-28 (accepted pre-existing risk, unchanged).** Other malformed configs that raise `ConfigError` / `PersistError` (missing section, bad int, parse error) still get a `.bak` copy and are reset to defaults with an empty `api_token`. This is out of scope here and is recorded for the Reliability milestone to decide whether every unreadable config should be fatal.

- The test setUp also restores `Seedsyncarr.logger` (class attribute) and the app loggers' levels, on top of handlers, signals and the keyfile path. **3. Reload test mechanics**
- The plan describes constructing once and then overwriting the file before `main()`. Doing that would make `main()`'s first construction fail immediately, which is not the reload path. Instead, `Seedsyncarr.run` is patched with a side effect that writes the bad settings.cfg (bytes recorded) and raises `ServiceRestart()`. `main()`'s loop then rebuilds the app, which is the UI-restart path. The test checks `run` call_count == 1, exit non-zero, bytes unchanged, no `.bak`, and that the file still fails to load. The logger exists from the first construction, so the `logger.error` branch is exercised.
- The bad file is written by generating valid text via `to_str()` with a placeholder password and swapping in the sentinel. This does not depend on how `to_str` handles `%`, so it survives Plan 119.1-06.

**4. Extra guard tests / commit**
- I added `test_parser_failure_classes_are_configparser_errors` to test_config.py. It checks that both interpolation classes subclass `configparser.Error`. Its name avoids `interpolat` so the plan's `5 passed` selection stays exact.
- `0cd06e7` adds `assertEqual(len(Config.secret_fields()), len(sentinels))` to the startup guard. It confirms one distinct sentinel per discovered field and brings the `Config.secret_fields()` grep count to 2.
